# GitHub issue connector design spike

This is the design note and one-repository prototype requested in [#1742](https://github.com/rohitg00/agentmemory/issues/1742). It reads public issue snapshots and sends them through the existing `POST /agentmemory/observe` capture path. It adds no core endpoint, storage scope, background service or release workflow. The package is private and has no published release.

Run it explicitly from a checkout with Node.js 20 or newer:

```sh
npm run build
node integrations/github-watcher/dist/bin.mjs --repo owner/repository --project hook-project
```

`--project` must match the label the checkout's hooks use; `AGENTMEMORY_PROJECT_NAME` supplies the same explicit override. `cwd` defaults to the invoking directory; use `--cwd /path/to/checkout` when invoking elsewhere. Preserve the same project mapping on reruns, including linked checkouts. The connector does not guess a project from `owner/repository`.

The default destination is `http://localhost:3111`. Override it with `--url` or `AGENTMEMORY_URL`. Supply `AGENTMEMORY_SECRET` if that destination requires a bearer secret; this prototype does not discover the daemon's credential files. `--since 2026-11-01T00:00:00Z` explicitly restricts source updates. `--max-pages` bounds traversal to 10 pages by default, with a maximum of 100; each page requests at most 100 records. Reaching the bound with another page outstanding is an incomplete run and exits with an error, retaining the counts of earlier confirmed captures.

The watcher and CLI are TypeScript ESM source. `npm run typecheck:github-watcher` checks their implementations and shared fingerprint helper with strict TypeScript settings; the normal build runs that check and generates the Node 20 ESM entrypoints and declarations in `integrations/github-watcher/dist/`. These generated files are ignored by Git.

## Compatibility with the initial prototype

The initial prototype used `gh_<repositoryID>_issue_<issueID>` sessions shared across project mappings. Existing captures in that namespace remain untouched: this correction does not move, relabel or delete their records. New captures use project-scoped sessions so the receiver's session project and search visibility agree.

The full 64-character event digest is unchanged, but the receiver deduplicates by project, session and event together. Replaying a previously captured revision into the new session therefore creates a separate observation; subsequent repeats in that new session deduplicate. Inspect and reconcile any captures made with the initial prototype before resyncing them. There is no automatic store migration or claim that old captures are absent.

The shared `fingerprintId()` retains its existing default 16-character digest. This connector explicitly requests the supported full 64-character digest for both revision IDs and project hashes; it never shortens previously emitted event IDs.

## Design decisions

1. **Events.** The spike uses a finite REST poll of one explicitly selected repository, serially following `Link` pagination. It selects all issue states and excludes rows carrying `pull_request`. Comments, pull requests, reviews, discussions and webhook handling are future work. A local process needs no public webhook receiver, while a deployed first release should prefer webhooks when available. There is no timer or automatic polling loop here.
2. **Authentication and private data.** GitHub repository metadata uses `GH_TOKEN`, then `GITHUB_TOKEN`, or the current `gh auth token --hostname github.com` credential. The metadata must explicitly identify a public repository. Issue-content requests are anonymous even when a token is configured: a repository becoming private after the metadata read must not grant this prototype private read authority. Private repositories are refused; private opt-in is not implemented. GitHub credentials never authenticate AgentMemory, and the destination secret never authenticates GitHub. Neither transport follows redirects. A future private connector needs explicit approval for the exact repository and destination, including shared/mesh destinations, before retrieving or forwarding private content.
3. **Rate limits and checkpoints.** Per-page ETags and validated page contents are cached only in process memory, after every page and capture in a run completes. Current pagination links on `304` responses are validated and used, including a newly appended page. Without pagination metadata, a cached nonterminal page follows its retained next link; a cached terminal page is refreshed unconditionally before concluding traversal. A `304` on the first page still conditionally reads later pages. Failed reads, partial traversals and unconfirmed captures do not replace the successful cache. Anonymous issue reads have GitHub's unauthenticated quota; this spike does not claim the primary-quota benefit of authenticated conditional requests. Rate-limit/error responses stop the run without automatic retries. An eventual scheduler must honor `retry-after`, reset and poll-interval headers. There is no persistent cursor or client outbox yet: a restart re-enumerates the selected source window, with server deduplication under the same identities. The optional `--since` is caller input and is never silently advanced.
4. **Deduplication.** An event ID is `gh_` followed by SHA256 of the JSON-encoded ordered tuple `["github-issues-v1", repository ID as string, issue ID as string, updated_at, title, body or empty string, state]`. JSON preserves text-field boundaries, including embedded NUL characters. The result satisfies the observe endpoint's 8–128 character alphabet; raw `owner/repository` contains a forbidden slash. Repository casing and renames change the locator rather than the event identity. Captured content changes within the same source timestamp still produce a new ID. Labels and other uncaptured metadata are outside this initial snapshot contract.
5. **Sessions and acknowledgments.** A deterministic `gh_<repositoryID>_issue_<issueID>_<projectHash>` session keeps a thread together across days and client restarts. The project hash is the full SHA256 of the JSON tuple `["github-project-v1", mappedProject]`; separate project mappings have separate sessions and search visibility. Only a successful response with the matching event ID, `accepted` or `duplicate`, and `state: completed` confirms a capture. A `200` duplicate may instead be pending, retrying or dead; those states stop the run, as do `202` retrying, rejection, malformed JSON or a lost response. Earlier confirmed captures remain in the error's progress counts. Unknown responses are not automatically resent. Inspect the destination before an explicit rerun under the same identities. Completion and its durability-window metadata do not prove a disk checkpoint or end-to-end exactly-once delivery. Replay protection depends on retained capture/observation records and unchanged project/session identities.
6. **Project and durable-state design.** Explicit mapping avoids confusing a GitHub repository name with the hooks' project identity. A first release should add a dedicated connector checkpoint function through iii-engine and `StateKV`, with a key binding repository ID, project, destination identity and schema version. Persist the outbox before sending, retain each event until its completed acknowledgment and the qualified backend durability window, then advance a completed-run watermark with an overlap for timestamp ties. Bind ETags to their complete URL/query and delivery state. Failed, unknown and dead-letter captures must remain reconcilable; changing destination or project starts a different checkpoint namespace. This is a proposed design, not a generic KV endpoint or persistence capability in this prototype.

## Limits and validation

GitHub's updated ordering can move records between pages during a run. A complete result means every returned page was traversed and its selected snapshots were acknowledged; it is not an atomic snapshot of the repository. Re-enumeration on subsequent explicit runs can recover source changes, subject to GitHub availability, the selected `since` window and retained deduplication state. Deletions and comment-only activity are not ingested.

The prototype treats issue text as source content, never as executable instructions. Error output reports progress and a failed event ID without copying GitHub error bodies or transport exceptions containing credentials.

The tests use deterministic GitHub transport fixtures and the real registered observe/capture functions with an in-memory KV/SDK dispatch double. They cover exact payloads, repeat/edit/restart identity, private visibility, pagination and conditional pages, incomplete capture states and partial failures. They do not qualify a live GitHub poll, native iii-engine durability, a shared store or hosted CI. The original existing capture-boundary controls remain separate from the requested new feature; a missing prototype module is not counted as a product failure.
